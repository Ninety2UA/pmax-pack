# Upgrade to v2.1.0

<img src="../diagrams/section-migration.png" width="72" height="72" alt="A migration bridge with an operator checkpoint">

This migration changes the reporting schema, reader identity and retention
policy. An operator runs two ladder passes with one signed review between
them. Pass 1 is two invocations of one pass: the phase-80 LOCAL parity stop,
then the phase-85 review stop, both using the same candidate digest.
Read the whole document, including rollback, before step 0. Commands
run from the v2.1.0 product root unless an anchor checkout is named.

Read in execution order: [guards](#prepare-the-guards-before-step-0),
[operator preparation](#step-0-operator-preparation),
[pass 1](#execute-pass-1), [pass 2](#execute-pass-2), then
[after-invariants](#gono-go-and-after-invariants). Keep the
[evidence queries](#evidence-query-recipes) and
[rollback appendix](#rollback-appendix) open during execution. Incremental
storage adds a supervised history drain and rebuild to each pass; budget it
with the [incremental variant](#incremental-variant-and-wall-time-budget).

![The upgrade separates preparation, candidate evidence, operator review, rehearsal, retention, and resume.](../diagrams/upgrade-sequence.svg)

### Invocation convention

Use `PROJECT`, `REGION`, `CONFIG_URI`, `CREDENTIAL_FILE` and `EVIDENCE` for the
operator's project, Cloud Run region, private config object, existing Ads
credential file and private evidence directory. Set `REGION` from the validated
config; this release constrains it to `europe-west1`. BigQuery location is `EU`;
it is separate from the Cloud Run region. Map the dataset names below through
the config. Keep identities, account identifiers, config objects and ladder
plan output private. `--plan` prints configured principals, including editor
addresses; never commit it.
`CONFIG_LOCAL` is the validated local config copy prepared in step 0, with
explicit storage; it is not the saved pre-upgrade config. `PMAX_ENV` is its
`env` value. `ALTER_DAY` is the UTC day of the proposed live retention ALTER;
`CUTOFF` is its ISO retained-day boundary, recomputed on the pass-2 day.
`AS_OF` is the published run's reporting date, read from its report; use it
for Q6 and the +24 h/+72 h reporting-window checks, not for loss acceptance.
Operator-written evidence records principals by count and role, never by
address; the config generation identifies the editor list. Capture raw IAM,
tokeninfo and audit responses only under a unique local scratch directory
outside the repository, summarize to counts or match/mismatch, then delete
the raw files. Create that directory with private permissions and cleanup:

```bash
set -euo pipefail
umask 077
EVIDENCE_SCRATCH=$(mktemp -d "${TMPDIR:-/tmp}/pmax-migration-evidence.XXXXXX")
: "${EVIDENCE_SCRATCH:?scratch directory was not created}"
trap 'rm -rf "$EVIDENCE_SCRATCH"' EXIT
```

Never write raw principals into operator-written `EVIDENCE` or a deployment
summary. Ladder-written records retain their own private contract.

## Prepare the guards before step 0

### Guard: resource scope

The operator verifies the project, billing, `app=pmax` label, parent
organization, region, exact account allowlist, timezone, private buckets and
all configured dataset names before permitting dataset creation in phase 20.
Review `deploy/deploy.sh --plan` with the real inputs and each proposed IAM
binding. The phase-00 assertions are the machine check. A plan still performs
read-only preflight calls; offline reviewers run `PMAX_DOCS_ONLY=1 bash deploy/tests/test_deploy_plan.sh </dev/null` for the document contract or `make deploy-test </dev/null` for the full PATH-shimmed deploy harness; those harnesses replace cloud commands locally.
No phase creates a project or links billing.

Check local CLI syntax before operator execution:

1. Syntax validation via `gcloud help <leaf_command>` and `bq help <leaf>`.
2. Parameter verification, including project, location, flags and whether a
   `--dry-run` or `--validate-only` flag exists for that exact leaf.
3. A dry-run proposal when that leaf supports it; use the ladder's
   `--plan` before a live pass and the phase-68 SQL dry run before rebuild.
4. Command proposal and authorization: the operator authorizes the printed
   human-run phases. Never use `--yes`, and never pre-confirm `85-review`.

Refresh both the CLI login and local Application Default Credentials
immediately before each pass, using `gcloud auth login --force` and
`gcloud auth application-default login`. They are distinct credentials
([authentication guide](https://docs.cloud.google.com/docs/authentication/provide-credentials-adc)).
Both credentials must identify the same operator account before each pass.
The retention subcommand uses ADC; the ladder's gcloud and bq leaves use the
CLI login. Verify CLI impersonation is unset and ADC is an unimpersonated user
login, with no credential-file override. Use the check below: compare the ADC
principal with the CLI account in memory and record only match or mismatch.
A mismatch or an unavailable principal is NO-GO. Finish interactive refresh
before starting a pass. Before invoking retention, the ladder verifies the ADC
user principal against the CLI account through tokeninfo and refuses a mismatch
or an unavailable verified principal. Do not wait for credentials, a pending
execution, or manual approvals inside a pass.

```bash
unset CLOUDSDK_AUTH_IMPERSONATE_SERVICE_ACCOUNT GOOGLE_APPLICATION_CREDENTIALS
gcloud config unset auth/impersonate_service_account --quiet
gcloud auth login --force
gcloud auth application-default login \
  --scopes=https://www.googleapis.com/auth/cloud-platform,https://www.googleapis.com/auth/userinfo.email
```

The following operator-only tokeninfo check keeps tokens and addresses in
memory, suppresses raw errors, prints only match/mismatch, and fails closed.
Set `EVIDENCE` in the environment before running it. Repeat it immediately
before each pass and after any reauthentication:

```bash
export EVIDENCE
uv run python - <<'PY_IDENTITY'
import json
import os
from pathlib import Path
import subprocess
import urllib.parse
import urllib.request

def capture(*args):
    return subprocess.run(
        args, check=True, text=True, capture_output=True
    ).stdout.strip()

matched = False
try:
    assert not os.environ.get('GOOGLE_APPLICATION_CREDENTIALS')
    assert not os.environ.get('CLOUDSDK_AUTH_IMPERSONATE_SERVICE_ACCOUNT')
    impersonation = capture('gcloud', 'config', 'get-value',
                            'auth/impersonate_service_account')
    assert impersonation in ('', '(unset)')
    adc_dir = Path(os.environ.get('CLOUDSDK_CONFIG',
                                 str(Path.home() / '.config/gcloud')))
    adc = json.loads((adc_dir / 'application_default_credentials.json').read_text())
    assert adc.get('type') == 'authorized_user'
    assert not adc.get('service_account_impersonation_url')
    cli = capture('gcloud', 'config', 'get-value', 'account')
    adc_access_value = capture('gcloud', 'auth', 'application-default', 'print-access-token')
    url = 'https://oauth2.googleapis.com/tokeninfo?' + urllib.parse.urlencode(
        [('access_token', adc_access_value)])
    with urllib.request.urlopen(url, timeout=30) as response:
        principal = json.load(response).get('email')
    matched = bool(principal and cli and principal == cli)
except Exception:
    pass
result = 'CLI/ADC principal match' if matched else 'CLI/ADC principal mismatch'
print(result)
with (Path(os.environ['EVIDENCE']) / 'operator-identity.txt').open('a') as record:
    record.write(result + '\n')
raise SystemExit(0 if matched else 1)
PY_IDENTITY
```


Record the check time and pass beside the match result. The check never writes
tokens, raw errors or addresses into evidence.

### Guard: schema and readers

The anchor is the recorded prior release image and its source checkout, named
in `deployments/<project>/rollback-anchor.txt`, that a rollback returns to.
Before any view drop or column addition, save the anchor image and its source
checkout, validate the saved config, record the observation triple, inspect
the six existing cohort schemas, and have a recovery-table location ready.
The observation triple is the row count, distinct observed days and latest
observed day of `raw_observations`, read with the
[observation baseline query](../operations.md#observation-baseline-query).
Verify the eight old views are present in `INFORMATION_SCHEMA.VIEWS`:

| Retired view | Replacement reporting table |
|---|---|
| `v_asset_performance` | `pmax_reporting.asset_performance` |
| `v_campaign_truth` | `pmax_reporting.campaign_truth` |
| `v_cohort_asset` | `pmax_reporting.cohort_asset` |
| `v_cohort_asset_group` | `pmax_reporting.cohort_asset_group` |
| `v_cohort_campaign` | `pmax_reporting.cohort_campaign` |
| `v_performance_asset` | `pmax_reporting.performance_asset` |
| `v_performance_asset_group` | `pmax_reporting.performance_asset_group` |
| `v_performance_campaign` | `pmax_reporting.performance_campaign` |

`v_asset_performance.asset_primary_status_reasons` (ARRAY<STRING>) becomes
`pmax_reporting.asset_performance.asset_primary_status_reasons_text` (STRING
joined with ', '), so UNNEST filters become string matches.

The reporting tables retain the retired views' dimensions and additive sums;
the [Looker guide](../looker.md#calculated-fields-per-reporting-table) gives
each table's calculated fields. The eight view definitions are preserved in
[`v2.1.0/retired-views/`](v2.1.0/retired-views/), outside the runnable SQL
tree. Keep them for reference only; do not point a dashboard at them.

Use the legacy-view inventory under [evidence query recipes](#evidence-query-recipes);
on an anchor upgrade it returns the eight names before phase 68, and it
returns no rows after phase 68.

Run the 60-day cutover query in the evidence recipes below. Zero readers is
required before phase 68. Repoint or retire an existing consumer before
proceeding; the eight views will disappear. Check schemas, partitioning,
clustering and ordinal positions against the rendered v2.1.0 DDL:
`deploy/deploy.sh --upgrade --plan` prints every phase-68 statement as a
`PLAN` line, and the live side is `INFORMATION_SCHEMA.COLUMNS` (ordinal
position, data type, mode, `is_partitioning_column` and
`clustering_ordinal_position`, per the
[COLUMNS view](https://docs.cloud.google.com/bigquery/docs/information-schema-columns))
plus `INFORMATION_SCHEMA.TABLE_OPTIONS`, read through the evidence query
runner. The six
column targets are `int_lag_prefix_campaign`, `int_lag_prefix_asset_group`,
`int_observation_cells`, `mart_cohort_campaign`, `mart_cohort_asset_group` and
`mart_cohort_asset`. The anchor's positional INSERTs fail while the added
`cohort_counting` column exists, including its own phase-25 dry run.

Set `PMAX_MIGRATION_REVIEWED=1` only after reviewing these changes and the
retention procedure. Phase 68 also requires a PAUSED Scheduler, no
live lease and no execution without a completion time; a terminal failed
execution is complete. If refused, settle the execution outside the ladder
and re-run. Never delete a lease to force progress.

### Guard: retention

Before pass 1, review the static managed retention inventory and run Q2 and
Q3 against existing datasets only. An anchor deployment may have no reporting
dataset yet; do not require the full live preview before phase 20 creates it.
Keep the resource-scope authorization above ahead of that dataset creation.
In incremental mode, phase 68 runs the full live preview after phase 20 and
before its clearing ALTERs. At the first phase-80 stop, run the full live
preview with the validated `CONFIG_LOCAL`; reporting now exists and no
phase-89 expiration has occurred. This is the operator checkpoint before
signing and pass 2. Repeat the preview before pass 2 if its date or config
changed. That checkpoint below shows the command.
For that static inventory, `partition_columns` and `expected_retention` in
`src/pmax_pack/retention.py` derive the table/partition map and expected
options from the schema specifications and rendered manifest without cloud
metadata reads. Match the existing tables to this map before pass 1.

Run this offline inventory from the product root with the validated config;
it loads the packaged manifest and performs no cloud metadata read:

```bash
uv run python - "$CONFIG_LOCAL" <<'PY_RETENTION_MAP'
import json
from pathlib import Path
import sys
import pmax_pack
from pmax_pack.config import load_config
from pmax_pack.retention import expected_retention
from pmax_pack.runner import load_manifest

config = load_config(sys.argv[1])
manifest = load_manifest(Path(pmax_pack.__file__).parent / 'manifest.yaml')
print(json.dumps(expected_retention(config, manifest), indent=2, sort_keys=True))
PY_RETENTION_MAP
```

In window mode only `date` or `click_date` partitions in raw and marts receive
`reporting_window_days + 1`. All `snapshot_date` and `observed_date` tables,
all ops tables, and all reporting tables must have NULL expiration. Landing
tables are separately managed and excluded. In incremental mode every managed
table expects NULL. Phase 89 applies only differing values, marts first, raw
last. The runtime only reports drift; changing a live window requires another
ladder run. Never change config alone and assume retention follows it.

For an anchor upgrade the live managed option map starts all NULL. If it does
not, stop and investigate before choosing a mode. The explicit exception is a
reviewed window-to-incremental switch: phase 68 clears exactly the click-day
options under `PMAX_RETENTION_CONFIRMED=never` and records their original values
in `migration-<digest>.json` before any incremental chunks are re-landed.
Phase 89 then verifies the all-NULL map and records an empty inventory.
A storage change on an already-upgraded v2.1.0 deployment is another v2.1.0
ladder run; it does not route through the v2.0.3 rollback appendix.

Before any clearing or expiration ALTER, verify that live raw, marts, ops and
reporting datasets have neither `default_partition_expiration_days` nor
`default_table_expiration_ms` set (also check the days representation).
Only the verification twins keep their seven-day table default. Refuse any
protected table on the ALTER list. Record every listed table's minimum day,
row count, additive sums, live loss count, and both raw/marts
`max_time_travel_hours`. A failed dataset-metadata call is NO-GO. If a
successful response omits `maxTimeTravelHours`, record the documented default
of 168 hours with `time_travel_hours_source: default`; when present, record
its value with `time_travel_hours_source: metadata`.
The rollback deadline is the ALTER timestamp plus the smaller of the two
time-travel windows. Preserve the earlier historical read timestamp as well.
The retention record carries `time_travel_hours` and
`time_travel_hours_source` for raw and marts, including each attempt. A
successful SCHEMATA_OPTIONS read supplies the metadata value or the 168-hour
default when `max_time_travel_hours` is absent. Independently read dataset metadata and record the
effective value and its source as above; an absent field in a successful
response is not a NO-GO. Compute the deadline from those recorded values,
using the earlier operator-derived deadline if the ladder's record differs.
Keep both values and flag the discrepancy. This follows the
[dataset API's documented default](https://docs.cloud.google.com/bigquery/docs/reference/rest/v2/datasets).
The step-0 loss count is a planning value only. Recompute Q1 and Q4 with the
pass-2 `ALTER_DAY` immediately before launch and accept the live loss count
again before phase 89. Record both planning and accepted values. On a TTY,
leave `89-retention` out of `PMAX_CONFIRMED_PHASES`; the phase-89 prompt is
the pause for a new-day recomputation before any ALTER. Off a TTY there is no
stop between phases 88 and 89: phase 00 requires `89-retention` in the list
and phase 89 runs right after 88, so recompute at launch and, when the pass
crosses a UTC-day boundary before the ALTER, record the post-ALTER count read
from `INFORMATION_SCHEMA.PARTITIONS` as the accepted loss (each crossed
boundary adds one expired click day per table); no re-invocation is needed.
Interrupting phase 88 is the only off-TTY stop; use the TTY
route when the recomputation must precede the ALTER. The typed
retention confirmation and recovery cutoff belong to that pass-2 acceptance.

Shortening expiration can expire existing partitions immediately. Physical
removal is asynchronous; NULL stops future expiration but does not restore
expired rows. Expiration runs from the UTC partition boundary, so the extra day
protects the oldest re-pulled date. Option values gate the ladder; observe
partition removal at +24 h and +72 h rather than waiting inside a pass.
[Partition expiration](https://docs.cloud.google.com/bigquery/docs/managing-partitioned-tables#set_partition_expiration)
documents these semantics.

### Guard: resume

A ladder generation is one attempt to carry a candidate through pass 1 and the
signed pass 2. Phase 25 (or phase 50, when 25 has not run) starts a new
generation when there is no continuation to reuse: none exists, the previous
one completed, or a different image is pinned. Its identifier is recorded in
`deployments/<project>/ladder-continuation.json`, and the generation completes
when phase 95 writes `resume-evidence-<digest>.json` carrying that identifier.

Before authorizing `95-resume`, require signed phase-85 evidence, successful
phase-88 rehearsal, recorded phase-89 retention, the alert checks below,
and a non-regressing observation triple. Resolve any HARD assertion failure,
observation regression or red anchor dry run through rollback. Budget,
freshness, report size or option mismatches require investigation and a fix
forward, not an automatic image rollback. A discrepancy is not permission to
bypass the gate. On upgrades, the phase-95 observation gate compares its after
reading with the preserved pass-1 baseline and records pass 1, active pass 2 and
after readings before resuming Scheduler.
The phase-90 flags attest observations made after valid alert-proof exists for
the active ladder generation; proof from an older generation of the same image
does not qualify. For the
first pass-2 run that produces proof, leave both flags unset and leave
`95-resume` out of `PMAX_CONFIRMED_PHASES`. The current `alert-proof-<digest>.json`, `alert-submission-<digest>.json` and
`lease-drill-evidence-<digest>-pass1.json` each carry the active ladder
generation. Phase 75 records that generation's pass-1 SKIPPED execution, and
phase 90 updates the alert policy and runs a fresh deliberately failed
execution for that generation. Proof validation requires all three `generation`
fields to match the active generation and rechecks the existing execution, run
and timestamp links. A retry may reuse a same-generation submission or proof,
but no previous generation's record can authorize resume.
Before replacing a current alert-proof, alert-submission or pass-1 lease-drill
record, the ladder builds and validates the new record in a temporary file,
preserves the current record's exact bytes beside it as `<record name without
.json>-<prior generation>.json`, records that archived path once under
`archived_alert_records` in the new generation's `ladder-continuation.json`,
and atomically renames the prepared record into place; an existing archive with
identical bytes is accepted on retry, while different bytes refuse with the
archive name. A refused validation removes that temporary file. On a TTY, verify the pass-2 failure email and
pass-1 SKIPPED silence at the phase-95 prompt before answering yes. Off a TTY,
the unlisted human-run phase stops before resume; verify both observations,
then set both flags to `1`, list `95-resume`, and re-enter with the same
reviewed digest and applicable signed evidence. Whenever `95-resume` is listed,
phase 00 requires valid existing proof and both flags, on and off a TTY. Either
flag set without proof refuses. A missing email keeps Scheduler paused.
`--plan` resolves the active ladder generation read-only before phase 00 and
validates alert-proof against it as the live pass does; when no active
generation exists, it prints `plan: no active ladder generation; alert-proof
validation runs on the live pass` and defers the proof check to the live pass.

Incident deletion is outside this ladder. An incident never edits or lowers a
preserved per-generation pass baseline. After an authorized deletion, re-record
the active `observation-before.json` through the phase-25 query and log the
deletion and new triple in the incident record. If an unfinished generation's
preserved pass-1 baseline predates the deletion, abandon that generation and
never resume it. A fresh generation may reuse the same reviewed image digest; phase 25 captures
its own generation-bound pass-1 baseline and the phase-95 observation gate
reads that path from the validated continuation record. `PMAX_FORCE_BUILD=1` with `PMAX_IMAGE_REF` unset starts a build and a
generation; it does not guarantee a new digest. If the same generation already has a conflicting preserved pass baseline,
stop; never delete or lower prior evidence, including baselines from earlier
generations. Preserve the prior
generation's pass baselines and evidence; active-file replacement alone cannot
lower its preserved pass-1 baseline. Use the public
[observation baseline query](../operations.md#observation-baseline-query).

## Step 0: operator preparation

Before step 0 changes anything, save Q7 for every fact table; repeat it after
phase 70 using the same closed-month boundary.

Start after that morning's scheduled run in the deployment timezone
(`timezone_override`) has completed.
The new-config upload and pass 1 through phase 70 happen in one sitting,
before the next scheduled morning: the anchor cannot parse cohort day 0 and
the new image needs phase 68's schema. Use the paused-morning fallback below
if this window cannot be kept.

1. Pause Scheduler and verify PAUSED. Wait outside the ladder until every
   execution has a completion time and there is no live lease. Record the
   current digest, numeric secret version and rollback pair before moving it.
   The rollback pair is the current Job digest beside the recorded anchor
   digest, not two inferred tags.
2. Save the live config bytes as
   `deployments/<project>/config-pre-v2.1.0.yaml` and its object generation as
   `deployments/<project>/config-pre-v2.1.0.generation.txt`. Describe the object
   before and after downloading and require the same generation. Keep a
   checksum. Bucket versioning is not assumed; the saved bytes are the backup.
3. Open `deployments/<project>/go-no-go-v2.1.0.md` and
   `deployments/<project>/paused-mornings-v2.1.0.md`. Use the generic checklist below
   and the public [paused-morning record](../operations.md#paused-morning-execution). Preserve evidence paths,
   UTC timestamps, operators and the pending status; never fill a live result
   from an estimate or planning measurement.
4. In a separate config copy set explicit `storage: window` or
   `storage: incremental`, `reporting_window_days`, and
   `cohort_days: [0, 1, 3, 5, 7, 14, 30]`. The ladder refuses a genuine upgrade
   without explicit storage. Window mode rolls off older click-day history;
   incremental mode retains it. Both preserve observations and entity history.
5. Validate with `load_config`, then upload using a generation-match condition
   on the current object to refuse a concurrent edit. Record the new generation.
   Do not pass `--config-file` to an upgrade; the GCS object is its config truth.
6. For an upgrade, have `deployments/<project>/rollback-anchor.txt` in place
   before pass 1; the readback recipe below compares the current image against
   it. Author it as one `key=value` line per field: `anchor_digest` (the anchor
   image's full digest reference, no whitespace), `anchor_source_commit` (the
   40-character private source commit), `anchor_public_tag` (informational)
   and `anchor_public_commit` (the public release commit, when one exists).
   The signed pass refuses at phase 00, and phase 88 refuses again, when the
   file is missing or the anchor checkout's HEAD matches neither recorded
   commit.

Use the [save/readback/upload recipe](#save-and-upload-the-config) below for
steps 1, 2 and 5.

Dataset values under `datasets:` are quoted strings matching BigQuery's
rule: letters, numbers and underscores, 1 to 1,024 characters
([dataset names](https://docs.cloud.google.com/bigquery/docs/datasets#dataset-naming)). An unquoted
all-digit value or boolean scalar is refused. `editors` and
`looker_service_agents` are lists of `user:<email>` or
`serviceAccount:<email>` members, not comma-separated strings. Every editor
must in practice be a Google Workspace or Cloud Identity user of one of the
listed organizations. Record editor count and config generation, never editor
addresses, in the migration record. Each listed organization supplies its own
Looker Studio service agent via Google's help page.
The config parser accepts either principal prefix in either list, but phase
40 accepts only `user:` editors and `serviceAccount:` service agents.

An explicit old `[1, 3, 7, 14, 30]` ladder overrides the new default. Adopt the
new ladder or explicitly accept the SOFT `no reconciliation pair` state.
Also record the `reporting window is not a lag bucket boundary` warning when
applicable. In incremental mode `start_date` must be the first day of a month;
when omitted it defaults to the first day of the month containing the run
date minus `reporting_window_days`. Window mode ignores `start_date` with a warning if supplied.

On every paused scheduled morning, from step 0 until phase 95, the operator
runs one manual `run` at the scheduled time in the deployment timezone. The UTC
execution timestamps, date in the deployment timezone, run ID, digest, report
URI, status and before/after observation triple go in
`paused-mornings-v2.1.0.md`. A rebuild does not
take observations and cannot substitute for this duty. If a night is missed,
record the gap; re-running tomorrow cannot reconstruct yesterday's reading.
Do not overlap a manual run with a ladder pass. If phase 70 cannot be reached
before the next morning, restore the saved pre-v2.1.0 config bytes, checked
against their recorded generation/checksum, before that morning and run the
manual execution with the compatible image and schema. Re-upload the new
config before resuming pass 1 and record both resulting object generations.
If phase 50 already installed the new image while phase 68 is incomplete,
settle a compatible image/schema using the rollback procedure before the
manual run; changing config alone cannot repair that state. During rollback
the anchor likewise runs only with the saved pre-v2.1.0 config.

### Save and upload the config

Pause Scheduler before the readbacks or any config/schema change:

```bash
gcloud scheduler jobs pause pmax-pack-daily --project="$PROJECT" --location="$REGION" --quiet
```

Then use the public [idle checks](../operations.md#paused-morning-execution)
and require PAUSED, settled executions and no live lease. Record the current image from the first
readback below and compare it with the anchor digest in the existing
`deployments/<project>/rollback-anchor.txt`. Read the numeric secret version
without accessing the secret payload:

```bash
gcloud run jobs describe pmax-pack-daily --project="$PROJECT" --region="$REGION" \
  --format=json --quiet > "$EVIDENCE_SCRATCH/job-before.json" \
  2> "$EVIDENCE_SCRATCH/readback.err"
jq -er '[.spec.template.spec.template.spec.volumes[]?.secret.items[]?.key] | if length == 1 and (.[0] | test("^[0-9]+$")) then .[0] else error("expected one numeric secret version") end' \
  "$EVIDENCE_SCRATCH/job-before.json" > "$EVIDENCE/secret-version-before.txt"
rm -f "$EVIDENCE_SCRATCH/job-before.json" "$EVIDENCE_SCRATCH/readback.err"
```

Require the value to match `sm_version` in the private deployment record.
The [secret-volume schema](https://docs.cloud.google.com/run/docs/reference/rest/v1/Volume#secretvolumesource)
uses each item's key for the mounted version; an alias or `latest` is not a
numeric pin. The next commands read the image and save the live config:

```bash
gcloud run jobs describe pmax-pack-daily --project="$PROJECT" --region="$REGION" \
  --format='value(spec.template.spec.template.spec.containers[0].image)' --quiet
gcloud storage objects describe "$CONFIG_URI" --project="$PROJECT" --format='value(generation)'
gcloud storage cp "$CONFIG_URI" "deployments/$PROJECT/config-pre-v2.1.0.yaml" --project="$PROJECT" --quiet
gcloud storage objects describe "$CONFIG_URI" --project="$PROJECT" --format='value(generation)'
shasum -a 256 "deployments/$PROJECT/config-pre-v2.1.0.yaml"
```

Require matching before/after generations and save that value in
`config-pre-v2.1.0.generation.txt`. Preserve that file and the checksum before
editing a separate config copy. Save the current value as
`CONFIG_GENERATION_BEFORE_UPLOAD`, validate the new local config, and upload
with a precondition. If the precondition fails, stop; never retry without it:

```bash
uv run python - "$CONFIG_LOCAL" <<'PY_CONFIG'

gcloud storage cp "$CONFIG_LOCAL" "$CONFIG_URI" --project="$PROJECT" \
  --if-generation-match="$CONFIG_GENERATION_BEFORE_UPLOAD" --quiet
gcloud storage objects describe "$CONFIG_URI" --project="$PROJECT" --format='value(generation)'
```

### Incremental variant and wall-time budget

The checkpoint hash changes once at this upgrade. Re-extract all monthly
chunks from `max(start_date, as_of minus 37 months)` through the current month
for each configured account, across [fact families A/B/C](../data-model.md#query-families); family D is the daily
snapshot. Quantify before pass 1: with month-aligned start S and last month E,
`month_count = 12 * (E.year - S.year) + E.month - S.month + 1`; multiply by
account count for account-months and by three for family-account-months.
A clamped first month starts at the 37-month extraction wall (the Google Ads API lookback
cited under [history checkpoints](../operations.md#history-checkpoints)).
Example:
2026-06-01 through 2026-09-25 is four months, four account-months per account
and twelve family-account-months. The omitted-start default at a 90-day
window on that date gives this same four-month plan. Record the actual
pending chunks and observed durations from the report.

Phase 70 first rebuilds/publishes, then starts one supervised incremental
run as the plan probe. Its `pending_after` is authoritative: zero ends the
loop after that one execution, which counts against
`PMAX_FIRST_RUN_MAX_EXECUTIONS` (default 3, allowed 1 to 10). Otherwise keep
supervised `run` executions under `PMAX_LEASE_MODE=first_run` until zero,
then perform the initial-history rebuild with
`--window-start=<clamped-start-date>`. The phase-70 implementation performs
this sequence; do not run an unrelated backfill beside it. Reporting still
publishes only the configured reporting window. Old cohort rows outside the
restated range may retain NULL `cohort_counting` and old labels until rebuilt.

Budget wall-time as `upgrade rebuild + N supervised runs + history rebuild`,
using the first run's measured seconds per completed chunk for the remaining
chunks. Reserve hours for a long history rather than the window-mode estimate
of a few minutes. The first-run lease budget is 25 hours; each default poll
budget is 1,440 polls at 60 seconds (about 24 hours), and the execution-count
bound is independent. Set a supervised stop time within the credential window.
A timeout retains execution evidence for adoption: wait outside the pass,
refresh credentials and resume, never launch a duplicate. If the bound is
exhausted with pending work, stop, investigate throughput and explicitly choose
a new supervised bound.
Apply this wall-time budget, credential window and supervised stop to pass 2
and every repeat of phases 68 to 80: each re-executes the full phase-70
sequence, including the supervised probe and initial-history rebuild in
incremental mode. Do not budget them as short validation-only invocations.

### Refusal and signature recovery

For a genuine upgrade, a refusal after 85 costs one more signature:
settle the cause, refresh both credentials, repeat phases 68 to 80 through the
ladder to the next review stop, sign the refreshed evidence, then re-run with
all pass-2 inputs. Never use `--yes`. Do not reuse the earlier review.

A fresh deployment has a separate continuation rule: same-digest SUCCESS
first-run evidence keeps the window default and skips the upgrade-only
observation and anchor branches until phase 95 completes the active ladder
generation. The completion record `resume-evidence-<digest>.json` contains both
digest and generation; a previous generation's same-digest marker cannot
complete a new generation. First-deployment continuations skip phase 25's
entire upgrade branch (Scheduler pause, previous-image capture, optional
snapshots, observation query and baseline writes) and create neither the active
reading nor either pass baseline; before first-run evidence exists, the
persisted generation origin still identifies a retry. If the signed
fresh-deployment pass fails at 88, 89, 90 or 95, retry with the same signature
and no anchor inputs; phase 85 revalidates the same evidence. A later deployment after completion follows the upgrade requirements, including
explicit storage and the anchor inputs, even when its new generation uses the
same image for a config-only change. It must obtain that generation's own
phase-75 pass-1 SKIPPED evidence and phase-90 failed-execution drill and proof;
the previous generation's alert records cannot authorize resume. Existing immutable
baselines remain protected from overwrite.

## Evidence query recipes

Use an operator query with a bytes cap, `app=pmax`, config `env` and
`stage=audit` labels. Save only sanitized results privately. This runner
applies to Q1 through Q7 and to every rollback SQL file; size the cap to the
reviewed scanned or recovered range. The example cap is 10 GiB:

```bash
EVIDENCE_BYTES_CAP=$((10 * 1024 * 1024 * 1024))
bq query --project_id="$PROJECT" --location=EU --use_legacy_sql=false \
  --maximum_bytes_billed="$EVIDENCE_BYTES_CAP" --label=app:pmax --label="env:$PMAX_ENV" \
  --label=stage:audit --format=json < "$EVIDENCE/query.sql"
```

Use actual config dataset identifiers in place of `PROJECT.RAW` and
`PROJECT.MARTS`. Repeat dataset-scoped queries for both. Inspect
`INFORMATION_SCHEMA.COLUMNS` for `is_partitioning_column = 'YES'`; constrain
all loss and boundary results to the config-derived click-day ALTER list.
For Q1 and Q4 append `--parameter="cutoff:DATE:$CUTOFF"` to the runner;
set `CUTOFF` to the ISO date computed from the pass-2 `ALTER_DAY` and window.
Keep step-0 planning results separately, then recompute on the pass-2 day
before phase 89. A UTC-day change follows the TTY or non-TTY route in the
retention guard; the report's `AS_OF` never substitutes for `ALTER_DAY` here.

In the integrated deployment checks, BigQuery CLI 2.1.38
`bq query --format=json` returned BOOL and INT64 result cells as strings. A jq check must compare a true
cell with `"true"`, not JSON `true`, and convert a count with `tonumber` before
numeric comparison. Keep this query-output convention separate from API or
gcloud JSON, whose field types may differ; inspect the returned schema before
writing a new evidence check.

**Q1, live partition loss and minimums.** Bind `@cutoff` to
`ALTER_DAY - reporting_window_days - 1`; it is the conservative retained-day
boundary. Inspect the boundary day's UTC expiration separately: it may also
expire during that day. List its count in the record, then include it in the
operator's maximum loss acceptance. Group partitions before summing so a
partition represented in more than one storage tier counts as one day.

```sql
WITH partitions AS (
  SELECT
    table_name,
    partition_id,
    SUM(total_rows) AS row_count,
    SUM(total_logical_bytes) AS logical_bytes
  FROM `PROJECT.RAW.INFORMATION_SCHEMA.PARTITIONS`
  WHERE REGEXP_CONTAINS(partition_id, r'^\d{8}$')
  GROUP BY table_name, partition_id
)
SELECT
  table_name,
  MIN(PARSE_DATE('%Y%m%d', partition_id)) AS minimum_day,
  COUNTIF(PARSE_DATE('%Y%m%d', partition_id) < @cutoff) AS older_days,
  SUM(IF(PARSE_DATE('%Y%m%d', partition_id) < @cutoff, row_count, 0)) AS older_rows,
  SUM(IF(PARSE_DATE('%Y%m%d', partition_id) < @cutoff, logical_bytes, 0)) AS older_bytes,
  SUM(IF(PARSE_DATE('%Y%m%d', partition_id) = @cutoff, row_count, 0)) AS boundary_rows,
  SUM(IF(PARSE_DATE('%Y%m%d', partition_id) = @cutoff, logical_bytes, 0)) AS boundary_bytes
FROM partitions
GROUP BY table_name
ORDER BY table_name;
```

**Q2, time travel and defaults.** Run at EU location. Save both settings,
the planned UTC ALTER time, and later the actual per-table deadline from the
retention record. Before phase 20, query only existing datasets; reporting
is not yet a required result on an anchor deployment. Read time-travel values
through dataset metadata and record `time_travel_hours_source` beside each
effective value. A successful response with no `maxTimeTravelHours` uses
168 hours and source `default`; a present field uses source `metadata`.
Only a failed metadata call is NO-GO for this check. The API exposes the field as `maxTimeTravelHours`
([dataset metadata](https://docs.cloud.google.com/bigquery/docs/reference/rest/v2/datasets)).

```sql
SELECT
```

```sql
  SELECT date, SUM(impressions) AS impressions, SUM(clicks) AS clicks,
    SUM(cost) AS cost, SUM(conversions) AS conversions,
    SUM(conversions_value) AS conversions_value,
    SUM(all_conversions) AS all_conversions,

    AND DATE_SUB(@as_of, INTERVAL 1 DAY)
  GROUP BY date
), actual AS (
  SELECT date, SUM(impressions) AS impressions, SUM(clicks) AS clicks,
    SUM(cost) AS cost, SUM(conversions) AS conversions,
    SUM(conversions_value) AS conversions_value,
    SUM(all_conversions) AS all_conversions,
    SUM(all_conversions_value) AS all_conversions_value
  FROM `PROJECT.REPORTING.campaign_truth`
  GROUP BY date
)
SELECT COALESCE(e.date, a.date) AS date
FROM expected AS e FULL OUTER JOIN actual AS a USING (date)
WHERE e.date IS NULL OR a.date IS NULL
  OR e.impressions IS DISTINCT FROM a.impressions
  OR e.clicks IS DISTINCT FROM a.clicks
  OR e.cost IS DISTINCT FROM a.cost

  OR IS_NAN(e.conversions) OR IS_NAN(a.conversions)
  OR IS_INF(e.conversions) OR IS_INF(a.conversions)

    + @relative_tolerance * GREATEST(ABS(e.conversions), ABS(a.conversions))
  OR (e.conversions_value IS NULL) != (a.conversions_value IS NULL)
  OR IS_NAN(e.conversions_value) OR IS_NAN(a.conversions_value)
  OR IS_INF(e.conversions_value) OR IS_INF(a.conversions_value)
  OR ABS(e.conversions_value - a.conversions_value) > @absolute_tolerance
    + @relative_tolerance * GREATEST(ABS(e.conversions_value), ABS(a.conversions_value))
  OR (e.all_conversions IS NULL) != (a.all_conversions IS NULL)
  OR IS_NAN(e.all_conversions) OR IS_NAN(a.all_conversions)
  OR IS_INF(e.all_conversions) OR IS_INF(a.all_conversions)

    + @relative_tolerance * GREATEST(ABS(e.all_conversions), ABS(a.all_conversions))
  OR (e.all_conversions_value IS NULL) != (a.all_conversions_value IS NULL)
  OR IS_NAN(e.all_conversions_value) OR IS_NAN(a.all_conversions_value)
  OR IS_INF(e.all_conversions_value) OR IS_INF(a.all_conversions_value)
```

For expired rows, calculate the cutoff from the actual expiration ALTER date
and the accepted window, including an expired boundary day.
An unqualified `FOR SYSTEM_TIME AS OF` timestamp defaults to
America/Los_Angeles, so the explicit UTC binding prevents a shifted recovery.
See the [historical-query timestamp rule](https://docs.cloud.google.com/bigquery/docs/reference/standard-sql/query-syntax#for_system_time_as_of).

```bash
bq query --project_id="$PROJECT" --location=EU --use_legacy_sql=false \
  --maximum_bytes_billed="$RECOVERY_BYTES_CAP" \
  --label=app:pmax --label="env:$PMAX_ENV" --label=stage:audit \
  --parameter="before_alter:TIMESTAMP:<UTC ISO with Z, before first ladder-68 ALTER for cohorts or first retention ALTER otherwise>" \
  --parameter="cutoff:DATE:<ISO date>" < "$EVIDENCE/recovery.sql"
```

`RECOVERY_BYTES_CAP` is the reviewed integer cap sized to that recovered
range; replace `PROJECT.RECOVERY` with the named, access-restricted EU dataset.

```sql
CREATE TABLE `PROJECT.RECOVERY.recovered_table` AS
SELECT *
FROM `PROJECT.DATASET.TABLE`
FOR SYSTEM_TIME AS OF @before_alter
WHERE click_date < @cutoff;
```
