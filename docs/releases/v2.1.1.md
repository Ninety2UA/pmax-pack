# pMax Performance Pack v2.1.1

A deployment-ladder patch on top of v2.1.0, from its first production upgrade. No runtime, SQL, or schema
changes: the v2.1.0 job image, reporting tables, and retention behavior are unchanged.

## Fixes in the upgrade rehearsal (phase 88)

- **Anchor cohort scripts run through stdin.** The rendered rollback-anchor SQL opens with a comment line.
  Passed as a positional argument, `bq` parsed it as an unknown flag and crashed, so phase 88 stopped before the
  Looker probes. Statements now travel on stdin, and the deploy harness rejects the old form the way `bq` does.
- **An empty dataset is no longer "invalid data".** `bq ls --format=json` prints nothing at all for a dataset
  without tables. The Looker probe resolver now reads an empty listing as no tables.
- **Empty datasets record what can be proven.** BigQuery answers Not Found for a missing table to every caller
  before checking permission, so a probe on a synthetic table name can never prove a denial. On an empty
  dataset the table read and capped SELECT are recorded as `NOT_PROVABLE_EMPTY_DATASET`, and the dataset
  describe denial is the proof. The probe contract in `deploy/iam.md`, `docs/operations.md`, and the v2.1.0
  migration guide says so.
- **Audit corroboration finds the denials.** The saved `gcloud logging read` filter matched on the request
  reason and on dataset resource names. BigQuery Data Access entries carry neither for a denied query, so the
  read returned nothing. The filter now bounds the reader principal and the probe window only. Each capped
  SELECT slot and the reporting CREATE TABLE slot are filled from the InsertJob denial that names the table or
  dataset. The direct-read and describe slots arrive pre-filled `NOT_LOGGED_BY_BIGQUERY`, because BigQuery
  writes no entry for those denials. A v2.1.0 probe record carries only `tables.getData` and `datasets.get`
  slots, which BigQuery never logs, so rerunning its command fills none of them. Convert it to the v2.1.1 slot
  shape (fill the capped-SELECT and CREATE TABLE slots from the InsertJob denials, and mark the direct-read and
  describe slots `NOT_LOGGED_BY_BIGQUERY`), or replace it with a fresh probe record.

## Image builds in Cloud Build by default

Phase 50 now builds the image in Cloud Build as the dedicated build identity, the way Google's App Reporting
Pack builds, so the operator machine needs no local Docker engine. Set `PMAX_BUILD_MODE=local` to build with a
local Docker engine as before.

- Phase 20 ensures the Cloud Build staging bucket (`<project>_cloudbuild`), and phase 40 grants the build
  identity read access on that bucket only. Without it, a build as the dedicated identity fails with a 403 on
  the uploaded source.
- The build runs a smoke check, so the image must start and print the CLI help before it is pushed.
- The Cloud Build upload honours `.gcloudignore`, which now excludes everything `.dockerignore` keeps out of a
  local build context, credentials included (`google-ads.yaml`, `.env` files, keys). The deploy harness keeps
  the two files in step.
- `.gcloudignore` is now an allowlist: the upload carries only the Dockerfile, `.dockerignore`, and what the
  Dockerfile copies (`pyproject.toml`, `uv.lock`, `README.md`, `LICENSE`, `NOTICE`, `src/`), so a credential at
  the product root stays local whatever its name. Phase 50 also pins source staging to
  `gs://<project>_cloudbuild/source`, the bucket phases 20 and 40 prepare, instead of gcloud's implicit default.
- The Docker CLI with buildx is still required for the published-manifest check, which needs no daemon.
  Phase 50 now configures the gcloud credential helper for Artifact Registry in both modes before that check, so
  a fresh operator machine no longer fails it on an anonymous registry token.

## Documentation

- The README opens with an animated hero of one nightly run, with light and dark versions and a still image
  for readers who prefer reduced motion. Its source and re-render script live in `docs/diagrams/hero-src/`.
- The README, data model, Looker guide, and example config now match the shipped pack: Looker Studio reads
  only the eight reporting tables, and no view sits in the reporting path.

## Upgrading from v2.1.0

Nothing to migrate. Deployments that already completed the v2.1.0 ladder keep running unchanged. Use v2.1.1's
`deploy/` for the next ladder run; it re-applies phases 20 and 40 idempotently.

## Compatibility

Same requirements as v2.1.0 (Python 3.12, Google Ads API v25 pin).
