# pMax Performance Pack v2.1.0

<img src="../diagrams/section-release.png" width="72" height="72" alt="A completed reporting generation, shown as an emerald seal over layered data">

v2.1.0 adds a bounded reporting dataset for Looker Studio, an explicit storage
choice, and asset cohort labels aligned with the App Reporting Pack (ARP). The runtime batches fact
loads and runs independent work concurrently. Operators retain the lease,
validation, provenance, parity, and signed deployment controls.

## Reporting and Looker Studio

Eight materialized tables in `pmax_reporting` replace the final ratio views.
They contain full click days from `as_of - reporting_window_days` through
`as_of - 1`, with 90 days as the default. The nightly run restates every
visible day. The partial run day remains in the marts.

Publication follows validation and replaces all eight tables in one
transaction. A HARD validation failure preserves the previous reporting generation.
Every reporting row carries `as_of` and `run_id`; separate charts can still
straddle a commit or retain cached results. Refresh every compared source and
require both fields to match, including after a same-day repair.

The dedicated `pmax-looker` service account has viewer access only to reporting
and project-level job creation. Each editor organization supplies its own
Looker Studio service agent; editors need managed identities and `actAs`
permission before editing a source. The [Looker guide](../looker.md) covers
credentials, sharing, cache freshness, date controls, probe evidence, and a
calculated-field recipe per reporting table. Looker Studio computes CPA, ROAS, and CTR
from sums and returns NULL for a zero denominator.

The following views are retired:

- `v_performance_campaign`, `v_performance_asset_group`, `v_performance_asset`
- `v_asset_performance`, `v_campaign_truth`
- `v_cohort_campaign`, `v_cohort_asset_group`, `v_cohort_asset`

`v_asset_performance.asset_primary_status_reasons` (ARRAY<STRING>) becomes
`pmax_reporting.asset_performance.asset_primary_status_reasons_text` (STRING
joined with ', '), so UNNEST filters become string matches.

Their SQL stays under
[`docs/migrations/v2.1.0/retired-views/`](../migrations/v2.1.0/retired-views/)
for historical reference. Internal `v_int_entities_*` views remain active.

## Cohorts and history

Newly written or restated cohort rows carry `cohort_counting`: `arp_calendar`
for assets, `google_lag` for campaign and asset-group rows. The default ladder
is `[0, 1, 3, 5, 7, 14, 30]`, with D0 only at asset grain. Action windows still
cap the ladder. The [cohort guide](../cohorts.md) defines the two countings,
the reporting-window edge, and the remedy for an unavailable asset window rung.
Legacy incremental rows outside the restated interval keep their prior labels
and may have NULL `cohort_counting`.

`storage: window` keeps a rolling click-day history; `storage: incremental`
retains older partitions and uses resumable monthly extraction chunks. Both
publish the same bounded reporting window. Incremental starts must be
month-aligned; an omitted start is the first day of the month containing the
run date minus `reporting_window_days`. Checkpoint hashes use family A, B, and C query text plus
API version, independent of start date.
The [query-family definitions](../data-model.md#query-families) list the
extraction queries in each family.

Window retention applies `reporting_window_days + 1` to tables partitioned by
`date` or `click_date`. It never expires snapshot, observation, reporting, or
operations partitions. Only an operator applies retention, and each apply
records the original table options, the altered tables, the time-travel
settings with their source, and a rollback deadline. The apply refuses when it
finds an expiring table it does not know. The runtime detects option drift
without changing it. See [storage](../storage.md).

The fetched interval bounds observation reads. Reports show the forfeited
asset-rung and restatement ranges for action windows that exceed it. Increasing
the window cannot recreate missed historical observations.

## Runtime and diagnostics

- Seventeen extraction queries spool rows through a bounded pool. All required
  account extraction must succeed before loads begin.
- Fact tables use one landing load and a transactional range swap per table;
  entity loads share the bounded load pool. In window mode, a swap refuses
  after the UTC `as_of` day to protect the oldest expiring partition.
- Ready SQL steps run concurrently within their stage. Assertions and report
  collectors are pooled; `--serial` supports comparison and diagnosis.
- The manifest's `depends_on` completeness audit checks declared dependencies
  against rendered SQL references, so missing producer dependencies fail the
  offline audit before deployment.
- `publish` follows `validate` in run, backfill, and rebuild modes. Parity does
  not publish.
- Rebuilds can use `--window-start` to derive earlier history, bounded by the
  37-month extraction wall. `--target-dataset` selects the paired marts and
  reporting destinations. Replacing a newer reporting generation requires
  `--allow-older-as-of`; dry runs record that check as not evaluated.
- `checkpoint reset` supports deliberate chunk recovery and refuses while a
  checkpoint streaming buffer prevents a reliable reset.
- Reports show dataset-qualified freshness, aggregated cohort gaps, retention
  drift, and an informational budget separating startup, stage span, tail,
  and process total. Job counts are submissions; reconciliation excludes
  child jobs.
- Load and backfill stage details record `load_path_jobs`. Backfill also records
  `pending_before` and `pending_after`, exposing the remaining monthly chunks.

Expect the first post-upgrade budget reading to exceed the informational
120-second stage-span target. Record two scheduled executions and their Cloud
Run timestamps before making a deployment-specific speed claim.

## Deployment changes

Read the [migration procedure](../migrations/v2.1.0.md) before running an upgrade.
Phase 68 prepares the new schema and removes retired views before its dry run.
Phase 70 rebuilds and publishes; incremental deployments begin with one
supervised run whose `pending_after` determines whether further runs are
needed. Phase 89 applies retention, confirmed with the exact echoed retention
value, after signed review and twin rehearsal. The operator records one manual
run each scheduled morning in the deployment timezone (`timezone_override`)
while scheduling is paused.

Config adds `env` with `prod`, `verify`, `parity`, or `ci` as its supported
values. Phase 80 verifies and records the `app=pmax` and configured `env`
resource labels on the datasets, report/config buckets, and daily Cloud Run
Job. It records the count of other label keys without retaining their values.

Before retention, the ladder verifies the user ADC principal against the
active CLI account and refuses a mismatch. Phase 88 drops the six twin cohort
tables once before the candidate rebuild, then rehearses the rollback schema
and restores the candidate shape.

Retries preserve generation-bound completion and alert evidence.
An explicit `PMAX_IMAGE_REF` wins; automatic reuse of an unfinished generation
requires the same repository HEAD within seven days. The ladder records active,
pass-1, and pass-2 observation evidence per digest. Listing `95-resume` requires
the alert-proof record and both alert flags at preflight, on or off a TTY.

Rollback clears expiration before restoring the anchor's cohort schema and
saved config, then uses the anchor checkout's own ladder. The anchor cannot
parse D0 and does not update `pmax_reporting`; dashboards freeze at the last
candidate `as_of`. Expired history needs a separate recovery procedure within
the recorded time-travel deadline.

## Data protection and compatibility

The raw and observation layers contain aggregate advertising performance and
entity configuration, without end-user identifiers. The [operations guide](../operations.md)
defines permitted readers, principal-level audit evidence, weekly credential
checks, offboarding, and the three incident-deletion cases across tables and
Avro copies. Share reports with named users or the client's domain, never link sharing.

Python 3.12, gaarf 1.18.3 (the
[Google Ads API Report Fetcher](https://github.com/google/ads-api-report-fetcher)
library), and Google Ads API v25 are unchanged. GAQL text is
unchanged. Dataset configuration values are string identifiers; editor and
service-agent lists use `user:` or `serviceAccount:` email principals. Upgrades
require an explicit `storage` value and an operator-reviewed migration.

The PRIMARY conversion basis is the campaign's conversion goals as Google
applies them, decomposed exactly by action; [What PRIMARY means](../data-model.md#what-primary-means)
defines its scope and the limits of goal evidence.

## Verification and remaining limits

The fixture suite exercises reporting publication and failure isolation, both
cohort countings, history rebuild, dependency scheduling, retention refusals,
and deployment evidence. SQL lint is advisory for documented partition-filter
warnings, and its pin fails on an undocumented one. It scans rendered manifest
SQL and does not scan SQL embedded in Python.

The release documentation includes updated architecture, data-model, cohort,
and runtime scenes, plus storage and upgrade scenes. The local gate commands
are in the [README](../../README.md#local-verification). Live probes, signed
review, retention evidence, and the two scheduled budget observations belong
to the operator deployment record.

A reusable Looker report template, an independent re-pull window, automatic
recovery of expired history, and a scheduler non-run alert remain outside this
release. A paused scheduler produces no failed execution, so the operator still
has to cover paused mornings by hand.
