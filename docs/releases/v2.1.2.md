# pMax Performance Pack v2.1.2

A documentation and deployment-ladder patch on top of v2.1.1. It shows how to build the Google Ads credential
from scratch and which Google Ads API access level a deployment needs. No runtime, SQL, or schema changes: the
v2.1.1 job image, reporting tables, and retention behavior are unchanged.

## Google Ads credentials from scratch

- **A new [credential guide](../credentials.md).** It covers the three pieces (the project's access level, a
  Desktop OAuth client in the pack's own project, and the refresh token of the user who manages the manager
  account), the Internal and External consent-screen routes, and every console and terminal step up to a
  passing probe. Two new diagrams show how the pieces meet and which access level fits which case.
- **Access levels now belong to the Cloud project.** Google sunset developer tokens on 2026-09-09. The access
  level comes from the project that owns the OAuth client, and a new project starts at Test, which reaches test
  accounts only. Three worked cases in the guide show when Explorer is enough and when Basic, with brand
  verification, is worth the work. The `developer_token` key stays in `google-ads.yaml` only because the pinned
  google-ads library requires it.
- **`scripts/mint_refresh_token.py`** mints the refresh token through your own client: the adwords scope,
  offline access, a forced consent, and the account chooser. It writes its output with mode 600, now also when
  the file already exists, and prints only the client's project number.
- The README has a new "Google Ads credential prerequisites" subsection, and the operations guide links to the
  credential guide.

## Deployment ladder

- **Phase 10 enables `googleads.googleapis.com`.** The Google Ads API has to be on in the project that owns the
  pack's OAuth client. Phase 00 probes the credential before phase 10 runs, so a first deployment enables the
  API by hand; the guide shows how.
- **`PMAX_OAUTH_PUBLISHING_STATUS` has two documented values:** `production` for an External app in
  production, and `internal` for an Internal app, which has no publishing status. Phase 30 still refuses
  `Testing`.

## Upgrading from v2.1.1

Nothing to migrate. Phase 10 runs idempotently on the next ladder pass and enables one more API. A deployment
whose OAuth client lives in another project keeps running for as long as that client exists. To move it,
create a client in the deployment's own project as the credential guide describes, check the project's access
level on the Google Ads API Overview page, and run a ladder pass with the new file. Phase 30 adds a Secret
Manager version, and the pass pins the job to it. Treat the move as a routine rotation and leave the old token
unrevoked, as the operations guide explains.

## Compatibility

Same requirements as v2.1.1 (Python 3.12, Google Ads API v25 pin).
